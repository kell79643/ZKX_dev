# Learning 规则

## 算子学习规则

本文件约束 `Learning/` 下所有算子学习工作。目标不是一次性总结整个 cuSignal，而是由学习者按算子逐个推进，从数学与物理原理进入 Python 源码，再进入 `cusignal_cpp` 的 CPU/GPU 复现代码。

### 一、总原则

1. **一次只学习一个算子。** 用户没有明确指定算子时，先请用户指定，不得自行批量展开多个算子。
2. **禁止一次性阅读全部源码。** 每次只读取当前算子直接对应的源码文件、导出入口，以及理解调用链所必需的少量直接依赖。不得为了“建立全局认识”遍历或通读整个 `cusignal-23.08.00`、`cusignal_cpp`、测试树或所有文档。
3. **严格分三阶段推进。** 当前阶段完成后先交给用户学习、阅读和提问；只有用户明确要求进入下一阶段，AI 才能继续。不得在一次回答中提前完成三阶段内容。
4. **以代码事实为准。** 数学公式、物理解释、Python 算法和 C++ 复现必须相互对应。无法从代码确认的推测应明确标注为“推测”，不得写成既成事实。
5. **学习文档默认使用中文。** 函数名、类型名、变量名、API、公式符号和源码路径保留原文。
6. **公式使用通用 Markdown 数学分隔符。** 行内公式使用 `$...$`，独立公式使用 `$$...$$`，不使用 `\(...\)` 或 `\[...\]`；确保 VS Code 内置 Markdown 预览可以直接通过 KaTeX 渲染。
7. **只修改学习副本。** 允许在 `Learning/cusignal-23.08.00` 中插入符合本文件规范的学习注释；`ZKX/cusignal-23.08.00` 和 `ZKX/cusignal_cpp` 始终只读。除非用户另行要求，不构建、不运行测试、不连接 ZQ500 服务器。

### 二、固定目录与文件命名

每个算子必须使用以下目录层级：

```text
Learning/operators/<模块名>/<算子名>/
```

例如：

```text
Learning/operators/waveforms/chirp/
```

每个算子目录中必须且只能维护以下三个学习文件：

```text
数学物理原理.md
python源码算法.md
cusignal_cpp_<算子名>复现逻辑.md
```

以 `chirp` 为例：

```text
Learning/operators/waveforms/chirp/数学物理原理.md
Learning/operators/waveforms/chirp/python源码算法.md
Learning/operators/waveforms/chirp/cusignal_cpp_chirp复现逻辑.md
```

命名规则：

- `<模块名>` 和 `<算子名>` 默认采用 `Learning/cusignal.md` 中的名称与大小写。
- 第三个文件名中的 `<算子名>` 必须与目录名完全一致，不得改成中文、缩写或自由描述。
- 不得用一个文件记录多个算子，也不得为单个算子另建 `README.md`、`notes.md`、附件或子目录。每个算子目录严格只有上述三个 Markdown 文件。

### 三、源码范围与优先级

#### 1. Python cuSignal 源码

默认以共享工作区中的以下副本为学习和注释对象：

```text
Learning/cusignal-23.08.00
```

以下目录是未经学习注释修改的只读基准：

```text
ZKX/cusignal-23.08.00
```

开始某个算子的源码阶段前，应先比较两个目录中当前算子涉及的目标文件。尚未加入学习注释的文件应完全一致；已有学习注释的文件，在只忽略符合下述固定标记的新增注释行后，原始内容仍应与只读基准逐行一致。如果发现原代码、原注释、空白或顺序存在其他差异，立即停止并向用户说明，不能自行覆盖或合并。

##### 学习副本的注释规则

在 `Learning/cusignal-23.08.00` 中只能**插入新的独立注释行**，所有原有内容必须保持不变，包括：

- 原代码和原注释的文字；
- 原有空行、缩进、空格和换行；
- 原有代码与注释的先后顺序；
- 文件名、目录结构和文件编码。

禁止改写、删除、移动或格式化任何原有行；禁止为了添加解释而在原代码行末尾追加文字；禁止运行会自动重排源码的 formatter。新增注释应放在所解释代码的正上方，并采用与上下文一致的缩进。

所有后来加入的学习注释都必须用半角尖括号 `<` 和 `>` 完整框住注释正文，并带固定的“学习注释”标识：

```python
# <学习注释：这里解释下一行 Python 代码的作用。>
```

C、C++ 或 CUDA 文件使用：

```cpp
// <学习注释：这里解释下一行 C++/CUDA 代码的作用。>
```

其他文本格式应采用该语言合法的单行注释符号，正文仍固定写在 `<学习注释：...>` 内。多行说明必须拆成多条独立注释，并保证每一行各自都有完整的 `<` 和 `>`：

```python
# <学习注释：第一行说明。>
# <学习注释：第二行说明。>
```

不得使用普通的 `# 说明`、`// 说明`、docstring、块注释或只有起止两行带尖括号的写法冒充学习注释。尖括号中的内容应解释代码语法、变量、公式映射或执行逻辑，不能只写“这里很重要”等无实质内容。

每次完成注释后必须核对：若从检查视图中去掉所有符合固定格式的学习注释行，剩余文件应与 `ZKX/cusignal-23.08.00` 对应文件完全一致。这个检查只用于验证，不得真的删除学习副本中的注释。

阅读范围按以下顺序逐步扩大：

1. 当前算子的公开导出入口；
2. 当前算子的函数或类定义；
3. 该定义直接调用的本项目函数、kernel 或 helper；
4. 只有在不读取就无法解释逻辑时，才继续读取下一层直接依赖。

不要读取与当前算子无关的模块。第三方库函数只解释当前调用所需语义，不扩展成第三方库全量学习。

#### 2. `cusignal_cpp` 源码

C++ 复现阶段默认以以下目录为准：

```text
ZKX/cusignal_cpp
```

只读取当前算子有关的：

- 公共头文件与对外接口；
- CPU/host/reference 实现；
- GPU/device/CUDA 实现及 kernel；
- 类型分发、显式实例化和必要 helper；
- 当前算子的直接测试或调用入口。

不得把只有测试包装、注册入口或类型转换的代码误称为算子核心实现。

##### `cusignal_cpp` 可变源码的版本规则

`ZKX/cusignal_cpp` 是持续开发和优化的活动源码，不能假设今天看到的实现以后仍保持相同行号和逻辑。学习笔记必须依赖 Git 提交保存历史，而不是把整份 `cusignal_cpp` 再复制到 `Learning/`。

1. 进入阶段三前，记录 `ZKX` 仓库的完整提交 SHA、提交时间、分支名，以及当前算子相关文件的 dirty 状态。
2. 若当前算子相关源码存在未提交修改，不得把它写成可追溯的正式版本。先向用户说明，并由用户完成或明确授权一个只包含相关改动的聚焦提交；无关文件 dirty 不影响读取，但必须如实记录仓库状态。
3. 每条 C++ 代码证据必须同时记录：完整提交 SHA、仓库相对路径、符号名和该提交中的行号。不能只写会随当前工作区变化的裸行号。
4. 历史源码通过 Git 读取，例如 `git -C ZKX show <SHA>:cusignal_cpp/<相对路径>`；不得为了保留旧实现而复制源码树、恢复工作区或覆盖当前优化代码。
5. `Learning/` 阶段始终只读 `ZKX/cusignal_cpp`。实际优化应在独立的开发任务中完成并提交，再回到学习文档记录新版本。
6. Git 提交是源码快照，学习文档是对该快照的解释；两者必须用 SHA 绑定。

### 四、三阶段学习流程

#### 阶段一：数学与物理原理

用户指定算子后，AI 先只做本阶段，并写入：

```text
数学物理原理.md
```

本阶段必须严格按“先研究通用原理，再研究 cuSignal 选择”的顺序进行。不能先看源码后反向把某一种实现写成该算子的全部数学物理原理。

##### 第一步：从代码之外检索通用数学物理原理

先在网络上检索该算子在数学、物理和信号处理领域中被普遍认可的定义、原理与典型算法族，并按“原理 1”“原理 2”……编号。检索要求：

1. 必须实际联网检索，不能只依赖模型记忆；
2. 优先使用原始论文、标准、大学教材或课程资料、权威机构资料，以及 SciPy 等相关项目的官方文档；
3. 关键定义和公式尽量由两个相互独立的可靠来源交叉核对；
4. 不把博客、论坛或搜索结果摘要作为唯一依据；
5. 每项原理都要就近标注可访问的网页链接，并在文末列出资料名称、作者或机构、链接和访问日期；
6. 如果不同资料采用不同定义、符号、归一化或分类方式，应分别说明，不能强行合并。

检索开始时先做“独立原理资格核验”：确认当前名称在脱离 cuSignal 代码后，是否确实对应一个公认的数学对象、物理模型或信号处理算法。若它实际只是 dispatcher、helper、索引生成器、参数换算函数或便捷别名，应明确写出“该 API 没有独立的数学物理原理”，再介绍它所调度或辅助的上位原理；不得为满足文档结构而虚构独立原理。

“通用原理”应独立于 cuSignal 代码存在。它可以是上位数学概念、物理模型、信号处理方法或公认的具体算法。文档至少列出：

1. 算子的通用定义、用途和典型输入、输出；
2. 原理 1、原理 2……各自解决的问题和彼此关系；
3. 各原理的核心公式及推导过程，不能只给结论；
4. 每个符号、参数、单位、维度和取值范围；
5. 离散形式与连续形式之间的关系；
6. 算法成立的前提、边界条件和特殊情况；
7. 参数变化对波形、频谱、精度或稳定性的影响；
8. 至少一个可手算或可直观验证的小例子；
9. 容易混淆的概念和常见误区。

##### 第二步：识别 cuSignal 23.08.00 实际采用的算法

完成通用原理检索后，再只读查看 `Learning/cusignal-23.08.00` 中当前算子的接口、定义和为识别算法所必需的直接调用。此时只做算法层面的识别，不提前展开阶段二的逐行语法讲解。文档必须列出：

1. cuSignal 算法 1、cuSignal 算法 2……；一个算子存在多个 method、模式或分支时应分别列出；
2. 每种算法的输入条件、执行步骤、核心公式和输出；
3. 支持该判断的源码相对路径、符号名和准确行号；
4. 哪些内容是数学算法本身，哪些只是数组处理、类型转换、边界检查或 GPU 工程实现；
5. 源码未采用哪些常见原理或算法，且只在对理解选择有帮助时说明原因。

##### 第三步：建立“通用原理—cuSignal 算法”关系

通用原理与 cuSignal 算法通常是“集合与子集”或“上位原理与具体实现”的关系，但必须根据证据判断，不能预设它们一定包含。使用下表逐项说明：

| cuSignal 算法 | 对应的通用原理编号 | 关系类型 | 公式与步骤对应 | 源码证据 | 结论 |
| ------------- | ------------------ | -------- | -------------- | -------- | ---- |

关系类型只能在有解释的情况下使用，包括：

- `属于`：cuSignal 算法是某个通用原理的具体算法或特例；
- `组合`：cuSignal 同时组合多个通用原理；
- `等价实现`：表达式或步骤不同，但数学上等价；
- `工程近似`：为离散计算、GPU 或性能采用近似；
- `扩展`：cuSignal 在通用原理上增加模式或功能；
- `未对应`：暂时无法纳入已检索原理，必须继续检索或明确保留疑问。

如果 cuSignal 采用的算法已经包含在“原理 1、原理 2……”中，必须明确写出“cuSignal 算法 X 属于原理 Y”，并指出对应公式、参数、分支和源码证据。如果一个算法被多个原理共同支撑，应逐项映射；如果不属于任何已列原理，不得硬套，应补充检索或标为“未对应”。

文档结尾应包含一组覆盖“通用原理辨析、cuSignal 算法选择、包含关系和源码证据”的自检问题，并在同一文档中紧邻给出逐题对应的参考答案。答案编号必须与问题编号一致，包含必要的公式推导、代码位置或判断依据，不能只写“是/否”、只复述题干或把答案留给用户自行查找。

完成后，AI 应简要带用户学一遍这些原理，然后停止，等待用户消化、提问或明确要求进入 Python 源码阶段。

#### 阶段二：cuSignal 23.08.00 Python 源码算法

只有用户明确要求学习 Python 实现后，才进入本阶段，并写入：

```text
python源码算法.md
```

本阶段必须深入到代码语法和执行逻辑，至少包含：

1. 当前算子的公开导入路径、定义文件、符号名和准确行号；
2. “当前算子的完整相关源码”章节：先按源码原有顺序完整摘录当前算子的函数或类定义，包括签名、完整 docstring、docstring 中的全部示例、函数体，以及该算子直接使用的本项目 kernel、helper 和必要的公开导出语句；
3. 函数签名，以及每个参数、默认值、返回值、dtype 和 shape 语义；
4. 从公开 API 到最终计算的调用链；
5. “逐行解释”章节：这里的“逐行”是覆盖完整性要求，不是要求把排版切成一行一个小节。必须按源码原顺序覆盖上一条摘录中的每一行非空内容，但默认以“最小完整语义块”为解释单位：多行函数签名、装饰器与定义、一次跨行调用、一个完整参数项、相邻声明、`if/elif/else` 分支、`try/except`、循环、一个完整公式、一个 kernel 定义或 docstring 中同一自然段/同一示例，应合并在同一个原文代码块中。只有语义确实独立且需要单独强调的单行才允许独立成块。每个语义块后按源码顺序解释块内每一行的语法、变量、执行顺序和数学含义；不得遗漏续行、闭合行、docstring、示例、注释或 kernel 字符串语句，也不得用总体概述掩盖其中某行；
6. 按源码执行顺序拆解控制流、分支、循环、数组操作和表达式；
7. 每条 Python/CuPy/C/C++/CUDA 语句的语法说明；
8. 数学公式与具体代码语句的逐项映射；
9. 使用的 FFT、插值、卷积、线性代数或 CUDA kernel 等底层机制；
10. 边界处理、异常检查、数值稳定性和 dtype 转换；
11. 时间复杂度、空间复杂度及可能的性能瓶颈；
12. 建议用户亲自阅读源码的顺序，以及每段代码应观察的问题；
13. 一组覆盖接口、语法、调用链、数学映射、dtype、边界和复杂度的自检问题，以及同编号、紧邻排列并带源码依据的参考答案。

这里的“完整相关源码”以当前算子为边界，不等于复制整个源文件：同一文件中的其他算子不得摘录；直接 helper 若同时服务多个算子，只摘录理解当前调用所必需的完整符号定义。不得使用省略号、伪代码或“其余类似”删减当前算子的源码或 docstring。若一个直接依赖过长，仍应完整摘录该依赖中被当前算子调用的符号，并逐行解释；只有第三方库内部实现不需要复制。

文档组织顺序固定为“代码定位与接口概览 → 当前算子的完整相关源码 → docstring 逐行翻译与解释 → 源代码逐行解释 → 调用链与算法总结 → 数学映射、边界、复杂度和阅读检查”。逐行解释应像 `Learning/operators/waveforms/unit_impulse/python源码算法.md` 一样，按“功能小标题 → 双行号定位 → 最小完整语义块原文 → 连贯解释”组织。小标题描述语义职责，例如“输入参数声明”“`idx is None` 分支”“调用 kernel 并返回”，不得批量使用“基准源码位置 321”“第 321 行”作为小标题。禁止把同一个自然段、调用、表达式或控制流机械拆成一行一个代码块；也禁止反过来把整个大函数只贴一次后用一段总述跳过内部语句。每个非空源码行应在逐行解释章节的某一个语义块中出现一次且只出现一次，使各语义块按顺序拼接后能够完整覆盖相关源码。空行无需单独解释，但完整源码摘录仍须保留原始空行。

逐行解释的固定格式参考 `Learning/operators/waveforms/unit_impulse/python源码算法.md`。例如：

````markdown
学习副本第 665-666 行，基准第 593 行：

```python
shape = np.atleast_1d(shape)
```

这里先解释 `np.atleast_1d` 的语法，再解释右侧求值、左侧重新绑定、shape 语义和后续影响。
````

其中定位行可以保留，但真正的解释对象必须是紧随其后的源码原文代码块。语义块没有强制固定行数：以读者能一次理解一个完整动作或概念为准，通常应包含相关的 2～15 行；若一个完整 docstring 段落、示例、分支或 kernel 自然超过该范围，应保持完整，不得为了满足行数机械拆分。连续多个仅用于闭合括号或续接同一表达式的行不得各自建立小标题。

代码引用必须给出带学习注释副本在共享根目录 `ZKX_dev/` 下的相对路径和准确起始行号，例如：

```text
Learning/cusignal-23.08.00/python/cusignal/.../file.py:123
```

必须同时补充 `ZKX/cusignal-23.08.00` 只读基准中的原始行号，避免新增学习注释导致行号偏移。完整源码摘录使用只读基准的原文。学习副本与只读基准行号只能作为代码块之前的辅助定位信息，不能代替代码块中的源码原文；逐行解释正文也不能只用裸行号指代被解释语句。行号必须在写文档时重新核对，不能凭记忆填写。

完成文档后，AI 应陪用户按调用链阅读源码并回答语法级问题，然后停止，等待用户明确要求进入 `cusignal_cpp` 阶段。

#### 阶段三：`cusignal_cpp` CPU/GPU 复现逻辑

只有用户明确要求学习 C++ 复现后，才进入本阶段，并写入：

```text
cusignal_cpp_<算子名>复现逻辑.md
```

##### 同一算子的优化演进记录

同一个算子优化后仍使用原来的第三个文件，不新增第四个文件，也不删除或覆盖旧版学习内容。文件采用以下结构：

## V2：第一次优化版本（<短 SHA>）

记录规则：

1. 第一次学习形成 `V1`；后续每个已经提交的优化版本按 `V2`、`V3` 顺序追加。

5. “版本差异与原理不变量”用表格比较算法结构、复杂度、内存访问、并行方式、精度边界和性能变化，同时指出哪些数学物理原理始终未变。

   解释必须面向“具备基本编程概念，但没有学过 Python/C++/CUDA”的开发者，按代码块内部顺序点明
   每一行或每组续行的语法、变量、执行时机、控制流、shape/dtype、数学意义、内存或同步影响。
   每个表达式都必须继续拆解其中的关键字、声明语法、类型、模板参数、命名空间、函数调用、成员访问、
   指针/引用、字面量及后缀、括号和运算符优先级、求值顺序、整数提升/转换、溢出或短路语义。例如
   `seed ^ (index * 747796405U + 2891336453U)` 必须解释 `^` 是按位异或而非乘方，括号先求值，
   `*` 先于 `+`，`U` 产生 unsigned int 常量，并说明无符号运算的模 $2^N$ 回绕及最终值的用途。
   禁止只写“先求值右侧”“更新变量”“调用函数”“按当前语言语法解析”“标识符决定数据血缘”等
   可套用于任意代码的模板句；不能只复述“这段完成某功能”，也不能让读者自行从源码推断语法。
   单纯罗列当前行出现了哪些关键字、运算符、字面量或标识符，同样不算语法讲解；解释必须说明这些
   语法元素如何组合成当前语句、为什么在此处采用这种写法，以及该组合产生什么类型和值。

   每个最小完整语义块的解释正文必须连续完成以下九层讲解，不能压缩成一条单句注释，也不能拆成
   与上下文无关的逐词词典：

   1. **语法结构**：指出该块属于声明、定义、初始化、调用、表达式、分支、循环、异常、模板、
      lambda、预处理、CMake 命令或 CUDA launch 中的哪一种，并解释开放/闭合符号和跨行续接关系；
   2. **名称与类型**：解释本块新声明和读取的名称、静态/运行时类型、`const`、引用、指针、模板实参、
      dtype、shape、字面量后缀、隐式/显式转换、对象所有权和生命周期；
   3. **执行过程**：按语言真实规则说明求值顺序、运算符优先级、参数绑定、短路、循环迭代、异常传播、
      Host/device 边界、线程索引、同步和内存读写；
   4. **任务语义**：说明输入值从哪个前置状态或配置而来，当前块形成什么中间量或证据，下一步由谁消费，
      并映射到本任务的数学、雷达、信号处理、精度、计时、稳定性或可视化职责；
   5. **初学者易错点**：针对当前代码指出至少一个可能误读之处，例如把 `^` 当乘方、混淆引用与指针、
      把 `float` 后缀忽略、误判整数除法、忽略 NumPy/CuPy Host/device 差别，或把 kernel launch 当普通调用。

   在上述五层中穿插并单列以下三层；它们是代码“为什么成立”的必要部分，不能由语法说明代替：

   6. **变量—公式—任务状态映射**：每个自定义参数、局部变量、成员和输出都要说明实际含义、单位、
      shape/dtype、取值来源、对应数学符号或公式步骤，以及被后续哪个变量/步骤消费。若它只是工程状态、
      资源句柄或证据字段而没有独立数学符号，必须明确写“无独立数学符号”并说明工程职责；
   7. **设计理由与替代方案**：不能停在“代码执行了异或/移位/复制/循环/调用”。必须解释为什么当前算法
      需要这一操作、它解决什么数值或工程问题、去掉或改变后会怎样，并在有实际可选实现时说明替代方案
      与当前选择的差异；无法从源码或可靠来源确认作者动机时，明确区分“可由算法推出的必要性”和
      “源码未记录的实现选择”，不得猜测；
   8. **数字常量逐项说明**：代码块中出现的每一个整数、浮点数、科学计数法数值及字面量后缀都必须
      逐项解释。说明其十进制/必要时十六进制含义、类型、单位、在公式或数组边界中的角色、为何采用该值、
      改变后的影响及来源。数学恒等常数应给出推导；算法固定常数应追溯论文/标准/原始实现；demo、规模、
      阈值和测试容差若只是仓库策略值，应明确写“源码未记录推导依据”，禁止臆造理论来源。重复出现的
      同一数字仍要说明当前上下文角色，不能只建立一张脱离代码的全局数字表。
   9. **任务条款—业务逻辑—代码落实对应**：这一层只保留在第 4 章“逐语义块逐行解释”中，Task1
      按赛题五项要求、Task2 按赛题六项要求建立固定条款编号。第 3 章完整源码中的学习注释不得逐块
      复制该业务模板。第 4 章每个代码语义块说明它直接或间接服务哪一条条款、在端到端业务流程中的
      角色分类、输入来源、输出消费者，以及“本块单独能证明什么、不能证明什么”；不得只写“属于
      StepN”或重复函数名。

   若某一层对当前纯闭合符号或纯注释确实不适用，应明确写出“不适用及原因”，不能省略。相邻续行必须
   与它所续接的声明、调用或表达式合并解释；禁止为 `)`、`});`、单个参数续行分别生成脱离上文的万能句。
6. 逐行解释部分的覆盖不等于机械地一行一个代码块。一个签名、跨行调用、控制分支、循环、完整公式或自然段应
   作为最小完整语义块；通常每块 2～15 行，语义不可分割时可更长。各语义块按源码顺序拼接后必须
   覆盖相关摘录的每一行非空内容一次且仅一次；续行、闭合括号、注释、异常分支和 kernel launch
   参数均不得遗漏。
7. 禁止以下不合格写法：只有完整源码而无逐行解释；只有拆散的语义块而没有连续完整源码；出现行号或行号表；只解释函数目标；
   用“其余类似”“见源码”“显然”跳过；一段解释笼统覆盖多个分支；只解释 GPU 而不解释 CPU
   reference，或只解释 wrapper 而不解释 kernel；一行源码配一句模板说明；只做词法/运算符清单而不
   解释它们如何组成当前语句；把跨行表达式的参数、闭合括号和调用主体拆开讲解。
8. 对头文件、纯声明、薄入口和 CMake，也必须逐行解释其对接口、编译目标和调用链的作用；可以按
   相邻声明或一个完整 target 组成语义块，但不能仅粘贴。
9. 每份 `stepN/cusignal_cpp实现逻辑.md` 必须在完整源码之后、第 4 章之前增加“函数总体处理方法”，
   按业务流水线解释主要函数、CPU reference、GPU wrapper、kernel、输入输出和前后步骤；同时增加
   “算子数学原理在当前任务中的实例化”，链接对应 `Learning/operators/<模块>/<算子>/` 的三份文档，
   给出当前调用所采用的公式、任务变量到数学符号的映射和参数实例化。只解释调用处需要的数学原理，
   不复制算子 Python/C++ 内部实现代码。正式算子调用必须进一步逐项写清调用实参到算子形参/数学
   符号的绑定、实际常量或配置字段、输入输出 shape/dtype、前后数据关系、当前分支/模式以及公式在该
   参数下的具体形式；不能只写一个通用公式或一句“调用某算子”。
10. 语法解释必须采用“先识别完整语句类别，再解释内部表达式”的顺序：先确定 `if/else`、`for/while`、
    `return/throw`、声明/定义、直接初始化、lambda、函数调用、模板和 CUDA kernel launch，再解释其中的
    比较、赋值、位运算和算术运算。禁止先按字符或正则表达式切分 `=`、`<`、`>`、`&`、`*`、`/`：
    `>=` 中的 `=` 不是赋值，声明符中的 `&/*` 不是按位与/乘法，模板 `<>/>>` 不是比较/右移，注释中的

    符号和语句终止符后才能结束；不能把 `};`、`});` 或返回表达式拆到下一块单独解释。
