# FP32 53算子两档规模复测说明

## 目标与输出合同

本复测只覆盖 FP32，将统一算子库 53 个算子分别映射到约 10K 和 100K 两档业务规模。
正式输出固定写入：

`正式数据/operator_scale_performance.csv`

该文件必须恰好包含 106 行数据（53 算子 × 2 档），并严格保持原表 10 列：

```text
operator,scale,input_dtype,timing_scope,gpu_mean_ms,gpu_p50_ms,gpu_p95_ms,gpu_p99_ms,cpu_mean_ms,cpu_gpu_speedup
```

实际 shape、参数、工作项、最大批内 CV 和证据绑定不挤入正式绘图表，而是由同目录自动生成
的 `operator_scale_performance_details.csv` 保存；十个入口的原始日志保存在容器
`test_all/operators/results/scale/<RUN_ID>_b*/<scale>/`。

正式 CSV 在完整门禁通过前继续保留历史 `unit_impulse`、`firwin` 两算子规模曲线，不能用
单批、探针或不完整的 53 算子结果覆盖。历史曲线说明了典型 crossover：FP32
`unit_impulse` 的 `cpu_gpu_speedup` 从 10K 的约 0.600 上升到 100K 的约 5.142；
`firwin` 则在 513～768 taps 之间由小于 1 跨到大于 1。新复测把这种随规模增长的趋势作为
合理性检查，但不把“所有算子 100K 必须大于 1”设为硬门禁；未跨越时必须结合算子复杂度、
实际 shape 和 `timing_scope` 如实解释，禁止修改或筛除实测数据。

## 规模映射

| 算子结构 | 10K/100K 映射 |
|---|---|
| 一维逐元素、窗口、波形和 FIR | 使用请求长度 10,000/100,000 |
| FFT 约束的一维/二维路径 | 使用相邻 2 的幂 8,192/131,072，并在详情表记录真实 shape |
| `correlate2d`、Kalman | 以二维元素数或矩阵工作量构造同量级边长 |
| `lfilter_zi` | 按高斯消元三次复杂度，以 `order³` 映射总工作量 |
| `firwin2` | 以 `numtaps × nfreqs` 总工作量映射，避免把两个维度同时放大到请求值 |
| `ambgfun`、`lombscargle` | 以输出网格或 `samples × frequencies` 总工作量映射 |
| `cfar_alpha` | 将规模映射为 reference cells 参数 |

因此，`scale` 是跨算子的展示档位；具体输入不能只靠该列反推，必须同时查详情表的
`input_shape`、`output_shape`、`parameters` 与 `actual_work_items`。

## 统计口径

- 每档 5 个独立批次；
- 每批 warmup 5 次、正式 20 次；
- 每个算子每档共 100 个 GPU 和 100 个 CPU 原始样本；
- `gpu_mean_ms`、`cpu_mean_ms` 为 5 个批均值的中位数；
- p50/p95/p99 使用 100 个 GPU 样本按 nearest-rank 计算；
- `cpu_gpu_speedup = cpu_mean_ms / gpu_mean_ms`；
- 一次 API 调用后同步，具体 `timing_scope` 按正式算子入口记录。

## gpu_02运行命令

先按 `AGENTS.md` 和 `docs/development/ZQ500_RUNTIME.md` 完成同步、`docker cp`、进入
`gpu_02` 以及 `source /zq500/sdk/env.sh`。在容器 `/tmp/ZKX_dev` 中执行：

```bash
cmake -S . -B build_scale_fp32 \
  -DUSE_DLFFT=OFF -DUSE_THRUST=ON \
  -DF_EVIDENCE_GIT_COMMIT=<当前git提交> \
  -DF_EVIDENCE_DIRTY_STATE=<clean或准确dirty标识> \
  -DF_EVIDENCE_TEST_TIME=<ISO-8601时间> \
  -DF_EVIDENCE_STATUS=passed

cmake --build build_scale_fp32 --target \
  f_bsplines_performance f_convolution_performance f_demod_performance \
  f_simple_batch_performance f_windows_performance f_wave_performance \
  f_estimation_design_performance f_filtering_performance \
  f_peak_radar_performance f_spectral_performance -j2

bash test_all/operators/run_task_f_scale_formal.sh \
  build_scale_fp32/test_all/operators \
  fp32_scale_<日期时间> \
  semi_final_tasks/交付/02_技术结果/图表数据/正式数据/operator_scale_performance.csv
```

最终成功标志必须为：

```text
[F5][SCALE-FORMAL][SUMMARY] rows=106 operators=53 scales=2 dtype=FP32 status=pass
```

没有该标志、任一批不是 53 条、任一性能记录不是 `status=passed`，或表头发生变化时，脚本
都会返回非零；不得把部分结果当成正式数据。

## 逐算子执行流程

正式实验按“一个进程、一个目标或一个算子、完成即检查”的顺序运行。不得再次直接启动
十入口×十批的长命令后长时间等待。每个模块先用 `--dtype FP32` 单独运行；filtering 等
包含多个重型算子的入口再用 `--operator NAME --dtype FP32` 拆分。单项日志仍放在对应
`<batch>/<scale>/` 目录，汇总器会读取该目录全部 `.txt`，不要求 53 条记录来自固定文件名。

单项命令模板：

```bash
cd /tmp/ZKX_dev/test_all/operators
mkdir -p results/scale/<batch>/<scale>
TASK_F_SCALE_ELEMENTS=<scale> \
TASK_F_BENCHMARK_WARMUP=5 \
TASK_F_BENCHMARK_ITERATIONS=20 \
timeout <按算子确定的上限>s \
  /tmp/ZKX_dev/build_scale_fp32_02e9f34/test_all/operators/<target> \
  --operator <operator> --dtype FP32 \
  > results/scale/<batch>/<scale>/<operator>.txt 2>&1
```

模块不需要拆分时省略 `--operator`。每次运行结束立即检查：

```bash
grep -c PERFORMANCE results/scale/<batch>/<scale>/<log>.txt
grep -c RAW results/scale/<batch>/<scale>/<log>.txt
grep SUMMARY results/scale/<batch>/<scale>/<log>.txt
```

单算子必须为 1 条 PERFORMANCE、40 条 RAW、`records=1 expected=1 pass=1`。模块入口的
预期记录数依次为：B-splines 3、convolution 2、demod 1、simple-batch 4、windows 8、
wave 6、estimation-design 3、filtering 14、peak-radar 6、spectral 6，总计 53。任一命令
超时、退出非零、记录数不符、缺少 SUMMARY 或出现 `pass=0/status!=passed` 时立即停止，
先修复该算子并跑正确性 smoke，再从该算子重测；不得继续后续算子。

## 全流程任务清单

1. **冻结源码与环境**：核对 Git commit/dirty 状态；完成标准同步、精确 `docker cp`、
   持久交互进入 `gpu_02`、SDK 初始化、`dlsmi` 和 CMake 版本检查。
2. **构建正确性门禁**：使用全新 Thrust 构建目录并绑定全部 F 证据字段；先构建受影响目标，
   再运行对应 E3 smoke。源码修复不得改变公开输入、输出 dtype/shape 或 cuSignal 语义。
3. **完成 b1 剩余 100K**：先检查维护前 `sosfilt` 日志，再逐项完成剩余 filtering、
   peak-radar 和 spectral；完成 53/53 与 2,120 RAW 总门禁。
4. **执行 b2～b5**：每批先完成 10K 的 53 个算子，再完成 100K；每个算子逐项检查后推进。
5. **运行五批汇总**：只在 5×2 个批次目录全部完整后运行
   `summarize_task_f_scale.py`，生成正式 10 列 CSV 与 details CSV。
6. **合理性复核**：检查相同算子从 10K 到 100K 的 GPU/CPU 时间、speedup 方向、真实 shape、
   timing scope 和 CV；异常必须回看 RAW 和源码，不能删除尾延迟或手工改数。
7. **交付收尾**：把原始日志/汇总证据取回交付证据目录，更新本说明、图表数据总表、
   AI 会话状态及引用正式 CSV 的技术文档，最后做 Git 聚焦提交。
