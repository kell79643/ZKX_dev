# 复赛答辩：高精度 CPU 参考讲述材料

## 约 90 秒主讲稿

我们原来已经有一套同数据类型的 CPU reference。它的作用是判断 GPU 有没有正确实现
FP32 或 FP16 的接口和算法契约，但它回答不了“这个数据类型本身损失了多少精度”。

因此我们没有修改正式算子目录，而是在测试支撑层增加独立的 CPU `long double`
高精度参考。现在有两个清楚的比较：GPU 对同 dtype CPU，用于实现正确性；GPU 对共同
原始高精度输入的 CPU 基准，用于判断 dtype 的总体精度损失。日志中还有一次编码后输入
诊断，它只用于分析误差来源，不是第三套 CPU reference。

我们选择了 7 个数值风险有代表性的算子，覆盖长乘加、递归滤波、频谱归约、重采样、
脉冲压缩和脉冲多普勒，并为 6 个算子增加 baseline、长序列和敏感输入。最终在 ZQ500 上
得到 40 条精度记录，全部通过。

结果最有价值的地方是：同 dtype CPU/GPU 一致，并不等于 FP16 没有精度损失。例如相关
算子的敏感场景中，FP16 相对高精度基准的最大绝对误差达到约 `1.45e-2`，而 FP32
保持在约 `5.87e-6`。这说明 GPU 实现没有偏离 FP16 契约，但 FP16 本身会随场景放大误差。

我们又把高精度参考接到 Task1 的脉冲压缩和多普勒链。FP32 和 FP16 在当前 32×256
单目标场景都正确定位到距离 bin 80、多普勒 bin 5；但 FP16 的链路误差约
`4.11e-3`，FP32 约 `2.61e-5`。所以最终工程决策是 Task1 和 Task2 正式路径保持
FP32，FP16 只允许在具体非敏感步骤通过业务指标复测后局部采用。

到这里停止继续给全部算子机械增加高精度公式，因为主要数值风险、深度场景和真实任务
传播都已覆盖，结论已经能够直接支撑数据类型选择。后续只有低精度路径、输入范围或业务
阈值变化时，再按风险补充。

## 评委追问速答

**为什么不能只用 CPU FP64 验证 GPU？**

因为这会把 dtype 量化损失和 GPU 实现错误混在一起。正确做法是保留同 dtype CPU 判断
实现一致性，再用高精度 CPU 单独量化总体精度损失。

**高精度 CPU 是性能基准吗？**

不是。它追求独立和准确，耗时不进入 CPU/GPU speedup。性能对比仍使用同 dtype typed
C++ CPU reference。

**为什么不覆盖 53 个算子？**

高精度参考的价值是风险发现和 dtype 决策，不是追求数量。当前已覆盖主要浮点风险和实际
Task1 传播；继续机械覆盖不会改变 FP32 正式决策。

**为什么整数没有做？**

整数需要先明确 scale、zero-point、反量化、舍入以及饱和或环绕语义。没有这些定义，
把整数输出直接和实数高精度结果比较没有统一工程含义。

**能否据此说 FP16 可用于 Task1？**

不能。当前固定单目标场景的峰值没变，只说明这个场景通过。敏感场景已经观察到 FP16
误差放大，所以正式 Task1 仍保持 FP32。
