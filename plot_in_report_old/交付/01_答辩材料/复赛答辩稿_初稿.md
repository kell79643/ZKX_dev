## 第 3 页：项目概述（约 55 秒）

本项目以 Python 版 cuSignal 的公开语义作为参考，用 CUDA C++ 实现高性能信号处理算子，
并把这些算子接入雷达目标检测和多域特征跟踪两条完整业务链路。

项目分为两个阶段。初赛阶段，我们完成了 12 大类、53 个标准算子的开发，并在 NVIDIA
平台完成两项任务的流程闭环和 CUDA 并行优化。复赛阶段，我们把工作重点从“算子能运行”
推进到“国产平台可交付”：完成 ZQ500 API、构建方式和科学计算库的适配，把 53 个算子
扩展到 FP32、FP16、INT32、INT16、INT8 五种业务输入，并建立算子、步骤和完整任务三级
验证体系。

因此，这个项目并不是 53 个相互独立的演示程序，而是一套可以被业务流程直接调用、能够
在 ZQ500 上构建运行并提供验证证据的工程。

[翻页。]

## 第 4 页：整体架构（约 55 秒）

[顺着页面从上到下讲三层，不要左右来回跳。]

整个工程分为三层。

最上层是任务封装层，包含两条完整流程。任务一是雷达目标检测与多普勒分析，共五步；
任务二是多域特征提取与定位，共六步。任务层负责串联算子和传递数据，不重新实现一套
算子算法。

中间是算子核心层，也是项目主体。这里统一维护 12 类、53 个正式 GPU 算子，每个算子
只有一个正式 API，通过 C++ template、类型 traits 和必要特化支持五种业务输入。同时，
每个 GPU 算子都有独立的 C/C++ CPU reference，用于正确性验证，不参与正式 GPU 业务
计算。

最下层是硬件适配层。CUDA runtime、FFT、随机数和构建差异都在这一层收敛，使上层任务
不需要感知 NVIDIA 与 ZQ500 的底层差别。当前正式交付重点是 ZQ500；NVIDIA 和 CPU
路径主要承担历史基线与参考验证，不应理解成三个平台的性能完全等价。

## 第 6 页：ZQ500 平台适配（约 1 分 35 秒）

[这是“平台迁移”和“科学计算库”合并页。按图从左到右讲，再补充底部四项。]

这一页是复赛最核心的迁移工作。整体路径是：上层 53 个算子先进入统一兼容层，再由兼容
层进入 ZQ500 原生工具链和平台科学库。我们主要解决了四类问题。

第一是 CUDA API。我们扫描了项目实际使用的 runtime API，对显存申请与释放、数据拷贝、
stream 同步、event 计时、错误检查和 kernel 启动逐项核对平台支持情况，并统一收敛到
`cuda_utils`。正式路径没有直接依赖底层 driver API，也没有引入平台明确不支持的虚拟
内存和外部资源互操作能力。

第二是 FFT 科学库。上层算子统一通过 `FFTInterface`，在 ZQ500 上由接口进入 `dlfft`，
业务算子不直接调用底层 FFT API。独立验证覆盖一维复数正逆变换、batch、原位和非原位
执行，以及非 2 的整数次幂输入补零。平台直接计算以 FP32 complex 为主，整数和其他受限
类型按照算子契约提升到安全的内部计算类型，再按规定输出；这不会改变对外的五类型接口。

随机数方面，我们也建立了 `rand_interface` 和 `dlrand` 后端，验证了 FP32 均匀分布、
正态分布和固定 seed 可复现。BLAS、DNN、SOLVER、SPARSE 在当前正式主路径中没有直接
调用，因此没有为了凑齐库名称而强行链接。

第三是 CMake 和编译工具链。项目按照 ZQ500 官方样例使用 `dlcc`，把 `.cu` 按 C++/CUDA
前端模式编译，并加入 `-x cuda` 和 DLI_V2 架构参数。最终证据中 298 条编译记录全部使用
`dlcc`，293 条 GPU 编译记录全部带有平台要求的编译和架构参数。

第四是平台限制兼容。我们把补零、类型提升、错误处理和资源管理放在统一接口层，避免
53 个算子各自重复写一套平台判断。最终 53 个独立算子目标、12 个类别目标、Task1、
Task2 和统一 `test_all` 均完成 ZQ500 构建运行，缺失和失败项为 0。

## 第 7 页：全维度测试验证体系（约 55 秒）

[围绕中央“四维度”，按左上、右上、右下、左下的顺序讲。]

为了避免只用“程序能跑”评价项目，我们建立了四维测试体系。

第一是功能正确性，检查算子语义、CPU/GPU 接口以及两条任务链路能否完整闭环。第二是
计算性能，分别记录算子 CUDA Event 时间、步骤端到端时间和任务整体时间。第三是多精度
适配，验证五种输入类型的真实调用、输出 dtype、误差和性能。第四是稳定性与资源占用，
覆盖非法参数、shape 不匹配、NaN、Inf、重复运行和内存趋势。

这里最重要的设计是：测试、Task1 和 Task2 都复用同一批正式算子，并且 GPU 输出与独立
C/C++ CPU reference 做全元素比较。这样可以避免测试走简化实现、业务走另一套实现，
也避免 GPU 结果和自身循环对比。

## 第 8 页：功能正确性与精度验证（约 55 秒）

[先指出图中蓝色是任务一、绿色是任务二，再解释本页是“代表算子/阶段基线”。]

这张图展示了两项任务所用代表算子的精度结果。上方蓝色部分对应任务一，包括脉冲压缩、
多普勒处理、CFAR 和模糊函数；下方绿色部分对应任务二，包括波形、滤波、相关、频谱、
小波、峰值定位和 Kalman 等算子。横轴是误差量级，越靠左表示误差越小，图中的结果均在
设定阈值以内。

这页的 MSE 图主要表达初赛和代表算子的阶段性正确性基线。复赛最终验收不只看这张图，
而是采用每个算子独立 CPU reference、全元素比较，以及绝对误差加相对误差组合容差。
任务一最终五步精度和语义指标全部通过，CTest 6/6；任务二六步和整体入口全部通过，
CTest 7/7。

任务效果方面，任务一准确定位到距离 bin 80 和多普勒 bin 5；任务二滤波后 SNR 从
16.75 dB 提升到 25.50 dB，最终 Kalman 估计与仿真真值的绝对误差约为 0.043，低于
0.18 的验收阈值。

在此基础上，我们又为 7 个数值敏感算子建立了独立 CPU `long double` 高精度参考，
并增加长序列、敏感输入和 Task1 两算子传播，共 40 条精度记录全部通过。这个验证区分了
“GPU 是否正确实现当前 dtype”和“选择该 dtype 后相对高精度基准损失多少”。实际结果
显示 FP16 在敏感相关场景的最大绝对误差可达约 `1.45e-2`，因此 Task1、Task2 正式
链路继续保持 FP32；高精度 CPU 只用于精度决策，不参与性能加速比。

## 第 9 页：多精度数据类型全量覆盖（约 1 分 30 秒）

[本页是数据重点。先讲左侧精度，再讲右侧性能，最后主动说“不是全部加速”。]

这一页是复赛五类型算子的最终量化结果。

左侧是精度。53 个算子分别支持 FP32、FP16、INT32、INT16 和 INT8，共形成 265 个稳定
测试 ID。每项都保存输入和输出 dtype、shape、参数、GPU 路径、CPU reference、容差和
失败位置。最终 265 项全部通过，共比较 12,865 个聚合元素，mismatch 总数为 0。最大绝对
误差出现在 `taylor`，约为 6.64×10 的负 6 次方，仍在对应算子的组合容差范围内。

其中有 89 项结果显示精确零误差。我们没有直接接受这些零值，而是做了路径独立审查、
非退化输入扰动和比较器负向测试，排除了比较器假阳性。框架还覆盖超容差、NaN、Inf、
shape、索引、mask、复数符号和复数布局等 8 类负向检查。非法输入会被明确拒绝，但主
测试进程能够继续。

右侧是 ZQ500 自编 benchmark。每项预热 5 次，再正式运行 20 次，并记录计时边界。265 项
GPU 平均耗时的跨算子均值约 1.66 毫秒，中位数约 0.335 毫秒；加速比均值约 9.49 倍，
中位数约 1.12 倍，其中 137 项快于同口径 C/C++ CPU reference。最高加速比是
`correlate/FP16`，约 358.17 倍。

我们不宣称所有算子都加速。标量或小工作量算子可能被 kernel 启动和同步开销主导，出现
CPU 更快是符合计算规律的。这也是我们保留全部结果，而不是只展示最好数据的原因。

[翻页。]

## 第 10 页：稳定性与异常处理（约 55 秒）

[不要把左图 37/47、15/19、47/47、28/28 说成当前最终 53 算子门禁。]

这一页展示的是早期按模块进行 1000 次循环的阶段性稳定性结果。它说明 Demod 和
Radartools 等模块在当时的用例下能够稳定完成重复运行，同时卷积和部分模块仍暴露出需要
继续排查的边界问题。

后续我们把稳定性判据从“程序是否跑完”提高到“同一进程中 CPU live heap 和 GPU 显存
是否存在方向性增长”。严格复核中，GPU 显存净增长均为 0；但是 ZQ500 `dlfft` 每次
execute 会留下约百字节量级的宿主侧 live heap，100 轮最小探针呈线性增长。plan 重建、
stream 变体和关闭自动 profiler 后仍可复现，定位指向当前平台 `libdlfft.so` 的执行路径。

项目的 `fft_thrust` 备用后端已经通过对照，能够消除该线性趋势。目前我们正在确定正式
长驻场景的 FFT 后端策略，并将在策略确定后重跑 53 算子、Task1 和 Task2 的严格长稳门禁。
